idle/readyを同一checkpointで確認してから実M4A lifecycleを完了した。production deploy後の
Cloudflare resource、Access、RunPod template、固定capacity、scale-to-zeroも独立read-backで
一致した。

production smokeは`workersMin=0`のまま短い非機密音声を1件受け付けた。provider queueには
入ったがWorkerは開始SLO内に1件も割り当てられず、次の5分Cron境界でjobとattemptは
`FAILED`へ収束し、provider jobは`CANCELLED`となった。manifestとartifactは作られず、
duplicate submissionもなかった。利用者の明示削除後はD1親rowの物理削除を確認した。
この結果はapplicationの安全な失敗回復を示す一方、production利用可能性の成功証跡ではない。

同smokeでは失敗状態がWebに表示されたが、notification outboxは作成されずDiscord通知も
なかった。[ADR 0058](../adr/0058-notify-terminal-failures-through-outbox-sweep.md)に従い、
未通知の`COMPLETED`と`FAILED`を通知境界で集中走査し、失敗通知済みjobのretry後も次の
terminal通知へ同じoutbox行を再利用する。変更後はapplication SHAが変わるため、直前の
candidate、staging acceptance、production promotionを新release evidenceへ再利用しない。

次のproduction smokeはscale-to-zeroのままjobを先に投入しない。production endpointを
明示承認付きで一時prewarmし、endpoint API上のactive Worker 1件についてcandidate image、
許可GPU、Secure Cloud、`desiredStatus=RUNNING`を照合する。同時にprovider queue 0、
healthのjob `running=0`、`idle + ready >= 1`、initializing、throttled、unhealthy 0を
満たした場合だけuploadする。成功・失敗にかかわらず`workersMin=0`へ戻し、active Workerと
queue 0をread-backする。失敗通知の実service確認もstagingで先に完了するまで、Statusは
Blockedを維持する。

[ADR 0059](../adr/0059-require-real-staging-failure-notification-acceptance.md)に従い、
formal stagingは正常M4Aに加えて音声を含まない合成破損M4Aを通常経路へ通す。exact
`FAILED`、現在versionのoutbox `SENT`、job/outbox送信時刻、failure fixture削除、
scale-to-zero復元を必須にする。最初のjob前は通常のqueue/in-progress/running 0とidle/ready
candidate Worker、またはADR 0062の3回安定したstale `running=1`を確認する。後者の次に
投入できるのは合成fixtureだけとする。二回目はADR 0061のrefresh証拠、job 0、異常state 0、
stale healthの3回連続観測を必須にする。短命acceptanceをschema version 3、
policy `adr-0059-v1`へ更新する。直前のcandidateとschema version 2のstaging evidenceは
このgateを含まないため、新release evidenceへ再利用しない。

今回のformal staging dispatch attemptは、job-level `env`から`runner.temp`を参照して
いたためGitHubのworkflow parserに拒否された。APIは`422`を返し、このattemptによる新しい
runもremote mutationも作成されなかった。failure evidence pathを利用する3 stepそれぞれの
`env`へ移し、全workflowでstep評価前の`runner.*`参照を拒否する静的検査と回帰testを追加
した。この修正を含む新candidateを発行するまでformal stagingは再実行しない。

修正後のformal stagingでは、正常M4A、合成破損M4Aのexact `FAILED`、各candidate Worker
照合、failure fixture削除受付、scale-to-zero復元まで成功した。通知read-backだけが、
WranglerのD1 ingestion用`--file`がCIで進捗行をstdoutへ出したため、JSON parse前に停止
した。acceptanceは発行されず、cleanupは`always()`で完了した。read-only queryを直接実行
する`--command --json`へ変更し、引数配列が`--file`を含まない回帰testを追加した。この
修正を含む新candidateとformal staging evidenceが成功するまでproduction promotionは
開始しない。

direct D1 query修正後のformal stagingでは、正常M4A lifecycleとcandidate Worker照合まで
成功した。handler outputはrefreshを要求したが、旧Workerとみられるinstanceがuptimeを
増やしたまま8分以内にidle/readyへ収束せず、失敗fixture前の二回目のprewarmで停止した。
failure fixtureとacceptanceは作成されず、`always()` cleanupによるscale-to-zero復元は
成功した。固定RunPod SDKを確認すると、outputのrefreshはcontrol plane向け`stopPod`だけ、
起動設定のrefreshはresult送信後のlocal job loop終了も行うため、[ADR 0060](../adr/0060-terminate-runpod-job-loop-after-refresh.md)
に従って両方を固定する。この変更はWorker image inputを変更するため、既存imageとcandidateを
再利用せず、新imageのbuild、offline check、SBOM、scanからやり直す。

ADR 0060を含む新candidateはlocal gate、offline check、SBOM、High/Critical scanを通過し、
formal stagingの最初のprewarm、正常M4A lifecycle、manifest、3成果物、download、
post-lifecycle candidate Worker照合まで成功した。Worker recordの作成時刻は同じだが
`lastStartedAt`が前進し、旧job loop終了後に`workersMin=1`を満たすcontainer再起動も
確認できた。一方、provider job 0かつGPU telemetryが処理中でない状態でもRunPod healthが
8分間`running=1`を返し、失敗fixture前の二回目prewarmはfail closedした。failure fixtureと
acceptanceは作成されず、scale-to-zeroと一時fixture cleanupは成功した。
[ADR 0061](../adr/0061-bind-post-refresh-prewarm-to-worker-restart-evidence.md)に従い、
初回条件は維持したまま、二回目だけrunner一時のWorker IDと起動時刻でrefreshを証明する。
job 0、candidate完全一致、異常state 0が揃う場合だけstale `running=1`を許容する。この変更は
Worker image inputを変えないため直前のimmutable digestを再利用できるが、新commitの
candidate、current-run SBOM/scan、formal staging acceptanceは再発行する。

ADR 0061を含む次candidateは、Pages専用tokenを同じstaging account/projectへlocal検証してから
GitHub Environmentへ設定し、全job、再利用Workerのoffline check、SBOM、High/Critical scan、
manifest発行まで成功した。formal stagingも全preflight、D1、Pages、R2、RunPod、Orchestrator
promotionを通過したが、最初の合成M4Aを作成する前のprewarmが8分でfail closedした。実jobと
acceptanceは作成されず、fixture cleanupとscale-to-zeroは成功した。直後のread-backはactive
Worker 0に対してhealth `running=1`を返し、初回でもprovider集計不整合が起こることを確認した。
[ADR 0062](../adr/0062-require-stable-candidate-evidence-for-stale-running.md)に従い、
candidate完全一致、job/異常state 0、同じWorker ID/起動時刻の3回連続観測をstale healthの
必須条件にする。次回timeoutは安全な最終counterを残す。この変更もWorker image inputを
変えないが、新commitのcandidateとformal staging acceptanceを再発行する。

## Ordered bootstrap runbook

[ADR 0022](../adr/0022-bootstrap-production-dependencies-before-applications.md)に従い、
初回productionでは依存resourceをapplicationより先に準備する。各番号を別checkpointとし、
前の番号のread-back検証が完了するまで次へ進まない。

1. Release freeze
   - release branchの差分をrelease修正だけに限定する。
   - version、lock、CI、staging evidence、未解決security findingがないことを確認する。
   - commit SHAを確定し、candidateを一度だけbuildする。以後のstaging/production deployを
     同じSHAとartifact digestへ結び付ける。
2. Read-only identity preflight
   - Wrangler、runpodctl、Node、pnpm、uvの固定versionを確認する。
   - Cloudflare/RunPodの認証先を確認する。secret値を表示・記録しない。
   - production resource名と予約originを追跡外planへ生成し、staging値の混入を拒否する。
3. Cloudflare resource bootstrap
   - production専用D1、private R2、Queue、DLQを作成する。
   - Queue consumer、DLQ、R2 Event Notification、CORS、lifecycleを設定する。
   - Pages project、Orchestrator Custom Domain、Access application/policyを準備する。
   - applicationはまだdeployせず、利用者trafficを許可しない。
4. RunPod image and endpoint bootstrap
   - release candidateのstaging acceptance済みimage digestを使用し、production用に
     再buildしない。
   - 同じimmutable digestからproduction templateとendpointを新規作成する。
   - 固定5090→4090候補、Flex、GPU 1、active workers 0、
     max workers 1、volumeなし、FlashBoot無効をread-backする。両候補availableで
     なければ停止し、jobは投入しない。stock tierとCommunity CloudでのGPU種別提供は
     release invariantにしない。実Workerの`secureCloud=true`はclaim前に検証する。
5. Secret registration
   - Web、Orchestratorのproduction専用secretを登録し、名前だけを検証する。
   - RunPod endpoint IDとAPI key、R2 key、Discord webhookはOrchestratorだけへ置く。
   - RunPod templateへ長期credential、token、webhookを置かない。
6. Migration and application deploy
   - D1 migration `0001`から`0009`を順に適用し、未適用が0件であることを確認する。
   - Orchestratorをdeployし、binding、Queue consumer、5分Cron、retention値をread-backする。
   - Web buildとPages Functionsを同じrelease SHAからdeployする。
7. Security smoke before user traffic
   - 未認証root、`/api/me`、preflightがAccess境界を迂回しないことを確認する。
   - 認証後のAPIでAccess JWT、Origin、CSRF、所有権拒否を確認する。
   - R2 CORSはproduction exact originだけを許可し、public read/listを拒否する。
8. RunPod and end-to-end smoke
   - staging acceptanceと同じ固定dummy mediaを使用し、初回workerのGPU、candidate image、
     Secure Cloudを確認する。
   - upload、Queue、submission、claim、heartbeat、manifest-last、finalize、3成果物、
     Discord通知を確認する。
   - duplicate、cancel、page close後の復元、offline fallbackを確認する。
9. Cleanup and go/no-go
   - dummy jobを明示削除し、安全期限後のD1/R2 cleanupを確認する。
   - R2不存在は[ADR 0021](../adr/0021-verify-r2-cleanup-with-uncached-listing.md)に従い、
     cache-busted Object API listingで判定する。
   - DLQ、Unhealthy/Outdated worker、未送信outbox、retention errorが0件であることを確認する。
   - deployment recordを完成させ、production trafficを許可するかを明示判断する。

## Stop and rollback conditions

次のいずれかを観測したら後続deployとtraffic許可を停止する。

- account、environment、resource、origin、AUDの不一致
- placeholderまたはstaging値の混入
- Access迂回、R2 public access、不許可CORS、secret名の不足
- migration不一致、Queue/DLQ/Event Notification/Cronの欠落
- image digest、template、registry credential、GPU候補、Secure Cloud
  invariantの不一致
- 固定候補のSecure Cloud提供欠落または一方がUnavailable
- claim前に実Workerの`secureCloud=true`を確認できない
- manifest/artifact integrity、所有権、CAS、cleanupの不一致
- secret、署名URL、録音内容、文字起こし本文を含むlog
- required check、dependency audit、container scanの失敗

初回bootstrap中のrollbackはtrafficを閉じたまま行う。forward-only migrationは削除せず、
applicationは直前の検証済みdeploymentへ戻す。RunPodは直前の検証済みtemplate/image
digestへ戻し、volumeやFlashBootを有効にしない。resource削除は自動化せず、対象が
production専用かつ未使用であることを別reviewで確認する。

## Release completion

production smokeとcleanupが成功した後だけ、release branchを`main`へ`--no-ff` mergeし、
release commitへ`v0.1.0` annotated tagを付ける。同じrelease branchを`develop`へ
`--no-ff` mergeし、両長期branchへ同じrelease修正を戻す。force-pushとtagの付け替えは
行わない。
