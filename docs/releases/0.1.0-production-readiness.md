## 2026-07-31 staging recovery E2E

既存staging endpointはAPI上data center設定を省略していた一方、Consoleでは単一
data centerだけが選択されていた。RunPod supportの案内に従う全data center選択の
隔離確認では米国のRTX 5090へ配置されたが、image pullが6時間を超えて`pending`となった。
`workersMin=0`へ戻した後もhealth集計とactive Workerの表示が整合しないため、旧endpointは
jobなし、scale-to-zeroのままprovider supportの調査証跡として保持している。

[ADR 0054](../adr/0054-use-explicit-datacenters-for-staging-recovery.md)に従い、既存candidate
のimmutable imageとRTX 5090、RTX 4090の固定順を使うstaging recovery endpointを1件だけ
作成した。`EUR-IS-1`と`EU-RO-1`を作成時に明示し、両方がHigh Supplyでexact selection
されていることをConsoleで確認した。作成応答と公式REST APIはdata center fieldを
省略したため、この手動read-backをproduction evidenceには使用しない。
`Security & compliance`はSecure Cloud切替ではなくdata center certification filterである。
recovery endpointは`Any`を維持する。両data centerはprovider metadata上GDPRとHIPAAに
対応し、片方はISO/IEC 27001とISO 14001にも対応するが、これらを実Workerの
`secureCloud=true` attestationの代替にはしない。

recovery endpointは約10秒でReadyとなった。Cloudflare staging runtimeだけを一時的に
切り替え、機密性のないaudio/mp4を実browserからuploadした。RunPodはjobを完了し、
claim前配置attestation、manifest-last、3形式のartifact、D1 finalizeが成功した。
利用者は成果物をdownloadし、正常な文字起こしを確認した。完了後はactive D1/provider
job 0、`workersMin=0`、Worker終了方向をread-backした。実resource ID、image参照、
録音、文字起こし本文は保存していない。

これはstagingの実利用経路が回復した証拠である。data center selectionと空のcompliance
filterは追跡対象planへ統合し、RESTとConsole-equivalent GraphQLを結合するexact read-back、
mutation前のrollback証跡確認、drift testを実装した。固定rendererでgit-ignored staging
planを再生成し、旧endpointをsupport証跡名へ、recovery endpointをcanonical名へrenameした。
両endpointのscale-to-zeroとrecovery capacityをrename前後に確認し、GitHub staging
Environmentのendpoint secretもCloudflare staging runtimeと同じendpointへ同期した。
workflowと同じread-only readinessとpromotion preflightは成功している。同一candidateの
自動staging acceptanceが完了するまで、今回の手動E2Eをproduction promotion evidenceへ
昇格せず、StatusはBlockedを維持する。
旧endpointを再試行せず、production resourceも変更しない。

同日、上記source/config修正を含むcandidate run `30598953293`は6 jobすべて成功した。
続くstaging run `30599328038`ではD1 migration、Pages、R2、RunPod、Orchestrator
promotion、live read-back、prewarm、実M4A lifecycleが成功した。E2E直後のcandidate
Workerが正当に`RUNNING`だった時点で、worker証跡stepがpromotion前のidle-only preflightを

[ADR 0055](../adr/0055-separate-worker-evidence-from-idle-promotion-preflight.md)に従い、
通常preflightを緩めず、post-lifecycle専用のread-only worker証跡verifierへ分離する。
専用test、CI構造検査、全local gate、secret scan、dependency auditが成功するまで新しい
candidateまたはstaging workflowをdispatchしない。前runはformal staging evidenceへ

同じ修正commitのcandidate publicationは、変更のないimmutable Worker imageを再利用し、

続くproduction promotionはread-only preflightを通過し、D1 migrationとR2 policyを冪等適用

StatusはBlockedを維持し、新しいworkflowをdispatchしない。

- Phase 1からPhase 7のstagingで検証済み機能

- Android Share Target
- production resourceのstagingとの共有

## Ordered bootstrap runbook

[ADR 0022](../adr/0022-bootstrap-production-dependencies-before-applications.md)に従い、
初回productionでは依存resourceをapplicationより先に準備する。各番号を別checkpointとし、
前の番号のread-back検証が完了するまで次へ進まない。

1. Release freeze
   - release branchの差分をrelease修正だけに限定する。
   - version、lock、CI、staging evidence、未解決security findingがないことを確認する。
   - commit SHAを確定し、candidateを一度だけbuildする。以後のstaging/production deployを
     同じSHAとartifact digestへ結び付ける。
2. Read-only identity preflight
   - Wrangler、runpodctl、Node、pnpm、uvの固定versionを確認する。
   - Cloudflare/RunPodの認証先を確認する。secret値を表示・記録しない。
   - production resource名と予約originを追跡外planへ生成し、staging値の混入を拒否する。
3. Cloudflare resource bootstrap
   - production専用D1、private R2、Queue、DLQを作成する。
   - Queue consumer、DLQ、R2 Event Notification、CORS、lifecycleを設定する。
   - Pages project、Orchestrator Custom Domain、Access application/policyを準備する。
   - applicationはまだdeployせず、利用者trafficを許可しない。
4. RunPod image and endpoint bootstrap
   - release candidateのstaging acceptance済みimage digestを使用し、production用に
     再buildしない。
   - 同じimmutable digestからproduction templateとendpointを新規作成する。
   - 固定5090→4090候補、Flex、GPU 1、active workers 0、
     max workers 1、volumeなし、FlashBoot無効をread-backする。両候補availableで
     なければ停止し、jobは投入しない。stock tierとCommunity CloudでのGPU種別提供は
     release invariantにしない。実Workerの`secureCloud=true`はclaim前に検証する。
5. Secret registration
   - Web、Orchestratorのproduction専用secretを登録し、名前だけを検証する。
   - RunPod endpoint IDとAPI key、R2 key、Discord webhookはOrchestratorだけへ置く。
   - RunPod templateへ長期credential、token、webhookを置かない。
6. Migration and application deploy
   - D1 migration `0001`から`0008`を順に適用し、未適用が0件であることを確認する。
   - Orchestratorをdeployし、binding、Queue consumer、5分Cron、retention値をread-backする。
   - Web buildとPages Functionsを同じrelease SHAからdeployする。
7. Security smoke before user traffic
   - 未認証root、`/api/me`、preflightがAccess境界を迂回しないことを確認する。
   - 認証後のAPIでAccess JWT、Origin、CSRF、所有権拒否を確認する。
   - R2 CORSはproduction exact originだけを許可し、public read/listを拒否する。
8. RunPod and end-to-end smoke
   - staging acceptanceと同じ固定dummy mediaを使用し、初回workerのGPU、candidate image、
     Secure Cloudを確認する。
   - upload、Queue、submission、claim、heartbeat、manifest-last、finalize、3成果物、
     Discord通知を確認する。
   - duplicate、cancel、page close後の復元、offline fallbackを確認する。
9. Cleanup and go/no-go
   - dummy jobを明示削除し、安全期限後のD1/R2 cleanupを確認する。
   - R2不存在は[ADR 0021](../adr/0021-verify-r2-cleanup-with-uncached-listing.md)に従い、
     cache-busted Object API listingで判定する。
   - DLQ、Unhealthy/Outdated worker、未送信outbox、retention errorが0件であることを確認する。
   - deployment recordを完成させ、production trafficを許可するかを明示判断する。

## Stop and rollback conditions

次のいずれかを観測したら後続deployとtraffic許可を停止する。

- account、environment、resource、origin、AUDの不一致
- placeholderまたはstaging値の混入
- Access迂回、R2 public access、不許可CORS、secret名の不足
- migration不一致、Queue/DLQ/Event Notification/Cronの欠落
- image digest、template、registry credential、GPU候補、Secure Cloud
  invariantの不一致
- 固定候補のSecure Cloud提供欠落または一方がUnavailable
- claim前に実Workerの`secureCloud=true`を確認できない
- manifest/artifact integrity、所有権、CAS、cleanupの不一致
- secret、署名URL、録音内容、文字起こし本文を含むlog
- required check、dependency audit、container scanの失敗

初回bootstrap中のrollbackはtrafficを閉じたまま行う。forward-only migrationは削除せず、
applicationは直前の検証済みdeploymentへ戻す。RunPodは直前の検証済みtemplate/image
digestへ戻し、volumeやFlashBootを有効にしない。resource削除は自動化せず、対象が
production専用かつ未使用であることを別reviewで確認する。

## Release completion

production smokeとcleanupが成功した後だけ、release branchを`main`へ`--no-ff` mergeし、
release commitへ`v0.1.0` annotated tagを付ける。同じrelease branchを`develop`へ
`--no-ff` mergeし、両長期branchへ同じrelease修正を戻す。force-pushとtagの付け替えは
行わない。
